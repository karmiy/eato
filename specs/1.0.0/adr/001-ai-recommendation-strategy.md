# ADR-001: AI 推荐策略

> 状态：已采纳  
> 日期：2026-02-17  
> 决策者：@user

## 背景

Eato 的核心功能是「帮用户决定吃什么」，需要根据：
- 参与成员的口味偏好、菜系喜好、饮食禁忌
- 当前位置附近的餐厅
- 预算范围

给出精准推荐。问题是：**如何在保证推荐质量的同时，控制 AI 调用成本？**

## 方案对比

| 方案 | 优点 | 缺点 |
|-----|------|------|
| **纯代码过滤** | 免费、快速 | 无法理解自由文本（如"最近减肥"）、无法解决偏好冲突 |
| **纯 AI 推荐** | 智能、灵活 | Token 消耗大、成本高、响应慢 |
| **分层处理** | 兼顾智能与成本 | 实现稍复杂 |

## 决策

采用 **「代码过滤 + AI 精排」分层架构**

### 高德数据的局限性

高德 POI API 返回的餐厅信息有限：

```json
{
  "name": "川味小馆",
  "type": "餐饮服务;中餐厅;川菜",  // 只有大类
  "address": "xxx路xxx号",
  "rating": "4.5",                 // 有时没有
  "cost": "68"                     // 人均，有时没有
}
```

| 高德能提供 | 高德没有 |
|-----------|---------|
| 餐厅名称、大类（川菜/火锅） | 辣度（微辣/中辣/特辣） |
| 人均消费（不一定有） | 口味细节（清淡/油腻） |
| 评分（不一定有） | 食材信息（是否有香菜、花生） |
| 距离 | 适合人群（减肥？约会？） |

**结论**：代码只能做基础硬过滤，**大多数场景都需要 AI** 来理解餐厅名称暗示的口味、匹配用户的自由文本偏好。

### 分层架构

```
┌─────────────────────────────────────────────────────┐
│                    用户请求                          │
│   参与成员、当前位置、搜索半径                         │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│              第一层：代码硬过滤（免费）                │
│   • 距离过滤（超出范围的不要）                        │
│   • 预算过滤（超出预算的不要）                        │
│   • 黑名单排除                                       │
│   • 基础大类匹配（用户选川菜，高德返回川菜）           │
│                                                     │
│   ⚠️ 作用：减少候选数量，省 AI Token                  │
└─────────────────────────────────────────────────────┘
                         ↓
              剩余餐厅（比如 50 家→15 家）
                         ↓
┌─────────────────────────────────────────────────────┐
│              第二层：AI 智能推荐（几乎必须）           │
│   • 理解餐厅名称暗示（"清真牛肉面" → 清真）           │
│   • 理解用户 notes（"减肥中" → 避免油腻）             │
│   • 解决成员冲突（A爱辣 vs B不吃辣）                  │
│   • 综合评分排序                                     │
│   • 生成推荐理由                                     │
└─────────────────────────────────────────────────────┘
                         ↓
              返回排序后的推荐列表（Top 10）
```

## Token 优化策略

### 1. 精简输入数据

```
// ❌ 不要这样
完整餐厅信息（名称、地址、电话、营业时间、评论...）

// ✅ 这样
{id, name, type, price, rating}  // 只传必要字段
```

### 2. 限制候选数量

```
代码预筛选后，只把 10-15 家餐厅传给 AI
```

### 3. 分场景选模型

判断是否需要 AI：

```
是否需要 AI？
├── 有 notes（"最近减肥"等自由文本） → ✅ 需要 AI
├── 多人有偏好冲突                  → ✅ 需要 AI
└── 单人 + 无 notes + 仅菜系匹配     → ❌ 可尝试代码排序
```

> ⚠️ **实际上大多数场景都需要 AI**，因为高德数据太有限，无法靠代码判断「川味小馆」到底辣不辣。

| 场景 | 模型 | 成本 |
|-----|------|------|
| 无复杂偏好（极少） | **不用 AI**，代码排序 | 免费 |
| 一般场景 | **Qwen-turbo** | 便宜（推荐） |
| 复杂偏好/多人冲突 | Qwen-plus | 中等 |

### 4. 缓存策略（列表缓存 + 逐个返回）

**核心思路**：缓存的是 AI 返回的「排序后的推荐列表」，而不是单个结果。

```
用户发起推荐请求
    ↓
检查缓存是否有效？
├── 有效 → 从缓存列表取下一个
└── 无效 → 调用 AI 获取新列表，缓存起来
    ↓
AI 返回排序列表（缓存）：[餐厅A, 餐厅B, 餐厅C, 餐厅D, ...]
    ↓
第1次摇一摇 → 返回 餐厅A（index=0）
用户点"换一家" → 返回 餐厅B（index=1，不调 AI）
再换 → 返回 餐厅C（index=2）
...
列表用完 → 标记缓存失效，下次重新调 AI
```

**缓存失效条件**（任一满足即失效）：
- 位置变化超过 1km
- 成员组合变化
- 超过 1 小时
- 列表中的餐厅全部用完

**好处**：
- 每次「换一家」不重复调 AI，省 token
- 同一轮推荐中不会重复出现同一家店

## Prompt 设计

```
系统：你是餐厅推荐助手。根据成员偏好，对餐厅评分(0-100)并简短说明理由。

输入：
成员：[{"name":"小明","likes":["川菜"],"avoids":["香菜"],"note":"减肥中"},
      {"name":"小红","likes":["粤菜"],"spicy":1}]
餐厅：[{"id":"r1","name":"海底捞","type":"火锅","price":120},
      {"id":"r2","name":"点都德","type":"粤菜","price":80}]

输出（JSON）：
[{"id":"r2","score":92,"reason":"粤菜清淡，适合减肥和不吃辣"},
 {"id":"r1","score":65,"reason":"火锅较油腻，但可选清汤锅底"}]
```

## 成本估算

| 项目 | 估算 |
|-----|------|
| 每次推荐输入 | ~500 tokens |
| 每次推荐输出 | ~200 tokens |
| Qwen-turbo 单价 | 输入 ¥0.003/千，输出 ¥0.006/千 |
| **每次推荐成本** | **约 ¥0.003（不到一分钱）** |
| 1万次推荐 | ≈ ¥30 |

## 结论

```
代码硬过滤（减少候选，省 token）+ AI 精排（几乎必须）= 精准 + 省钱
```

**关键认知**：
1. 高德数据有限，大多数场景需要 AI 才能精准匹配
2. 代码过滤的价值是「减少候选数量」而非「替代 AI」
3. 缓存排序列表 + 逐个返回，让「换一家」不消耗额外 token
